# Verify the job isolation boundary instead of assuming it

[ADR 0001](0001-use-scale-sets-with-platform-executors.md) chose Firecracker microVMs as the strong Linux isolation path and kept Docker as a trusted-only on-ramp. That decision stands. This ADR settles the three things that decided whether it was real: how the job network boundary is defined and proved, what may survive between jobs, and what a Worker has to demonstrate before it is allowed to advertise capacity.

The Firecracker executor already gave each Attempt a fresh guest kernel, a copy-on-write root prepared from the image chain ID, MMDSv2 credential delivery, a scoped containerd lease and guaranteed teardown. What it did not have was a host it could actually run on, or any way to tell a correct host from a broken one. `Preflight` checked that a CNI configuration file _existed_; it never looked at what that file said. A host whose network policy had been edited, or which had never had one, passed readiness and ran jobs.

## Decision

**The network policy is code, and readiness verifies it.** `apps/runtime/internal/netpolicy` renders both halves of the job network — the CNI configuration list and an nftables table — and verifies both. The CNI chain is `ptp`, `firewall`, `tc-redirect-tap`: `ptp` rather than `bridge` because a bridge puts every guest on one layer 2 segment, where guest-to-guest traffic never reaches a routing hook and cannot be filtered at all. The nftables table `inet runner-center` drops guest traffic to other guests, to the host itself, and to RFC1918, CGNAT, link-local and the other special-purpose ranges, with an explicit allowlist for destinations an operator declares and an optional allowlist-only egress mode. Every rule carries a stable comment, and verification requires each chain to hold exactly its expected rules in order, so a removed rule, a reordered rule and an inserted unmanaged rule all fail readiness.

The host provisioner renders these files by running the same `runner-center-runtime` binary that later verifies them. There is no second source of truth to drift from, and no hand-maintained example configuration that can quietly diverge from what the code demands.

**Nothing writable survives a job.** The Docker executor's Profile-wide pnpm volume is removed. It was mounted read-write into every container on a Profile, which is a direct cross-job poisoning path: one job writes a compromised package into the content-addressable store and the next job installs it. The Firecracker executor never had an equivalent and does not gain one.

Cross-job dependency caching belongs outside the disposable boundary, and GitHub already runs exactly that service: `actions/cache` is authenticated, scoped by repository, branch and key, and enforces the fork-PR restriction that matters most. Reaching it is one of the destinations the egress policy allows. Building a second cache service inside EraInfra would mean re-implementing that scoping — and EraInfra is in a strictly worse position to do it, because a scale-set Attempt is created _before_ GitHub binds a job to it: the controller receives only a desired runner count, and the repository, ref and event arrive later, in `JobStarted`. A per-repository cache device cannot be attached at boot because at boot the repository is not yet known. Warm state therefore comes from the digest-pinned Image Release, which already prewarms the runner, action archives, Node and pnpm.

**EraInfra owns its own host namespace.** Firecracker uses a dedicated containerd instance with its own socket, content store and devmapper thin-pool, and its own CNI plugin and configuration directories under `/opt/runner-center` and `/etc/runner-center`. A Worker that also runs Docker or Kubernetes keeps both untouched, and the provisioner's `--uninstall` reverses exactly what it added. Sharing `/etc/containerd/config.toml` or `/opt/cni/bin` would have let an unrelated component redefine the network EraInfra had just verified.

**Readiness reports evidence, not a boolean.** `Preflight` returns a structured report — the isolation technology, the security boundary, one named result per prerequisite, measured hardware, thin-pool headroom and the network policy in force — and does not stop at the first failure, so an operator provisioning a host sees every broken check at once. The Worker forwards that report; the control plane stores it and refuses a "ready" report that contradicts itself: a failing check, a boundary the executor cannot provide, or writable storage shared between jobs. The dashboard shows the real boundary per Profile and the exact failed check per Worker. Thin-pool headroom joins CPU and memory as an admission dimension, because a pool that fills mid-job fails the job after the work is already done rather than declining it up front.

**Admission keeps exactly sized small hosts useful.** CPU and memory normally admit work inside a 90% envelope, leaving headroom for the host. When a host has no more of one dimension than a work item requests, the scheduler compares against the full reported dimension instead: an exact fit can run one item, an undersized host still cannot, and the slot and reservation checks prevent a second item. Without this deliberate full-host carve-out, applying 90% to a machine sized exactly for one Profile would make that machine unable to run anything.

**The image's privilege model follows the executor boundary.** The `runner` user in `images/ubuntu-24.04-js` has passwordless sudo so a Job or Experiment can become root inside its disposable environment. Firecracker contains that privilege inside a fresh guest kernel; Docker contains it only inside a container that shares the host kernel, and the host Docker daemon can inspect container state. Docker Profiles therefore hold only mutually trusted jobs in one trust domain and are not the isolation path for untrusted code.

**Tart host-key attestation has an explicit trust-on-first-use fallback.** The macOS provisioner first asks Tart's guest agent for the SSH host key over vsock and otherwise reuses an earlier Image Release pin. If vsock does not answer and no pin exists yet, the first SSH connection uses `accept-new`, persists the presented key, and makes later runs strict. A local attacker on the Tart bridge can poison that first persisted pin, and strict checking later does not authenticate it; an operator must verify it through a trusted guest console or working vsock, or restore attestation, remove the pin and rerun to enroll the attested key. A changed key still fails once either out-of-band attestation or an earlier pin exists.

## Fireactions: integrate, upstream, fork or replace

Re-evaluated against the working implementation rather than against a plan. **Keep Fireactions as a reference; do not adopt, fork or vendor it.** The parts of it worth having — the Firecracker plus containerd-devmapper plus CNI host layout — are exactly what this ADR turns into a provisioner and a verified policy, and that is roughly 400 lines of shell plus one Go package. What adopting Fireactions would bring with it is a second control plane: its own pool model, its own GitHub ownership scope and its own image policy, all of which duplicate or weaken Convex's scheduler, the multi-platform Profile contract, and the scale-set protocol EraInfra already speaks. Forking would mean owning that surface without the upstream. Upstreaming the verification work is attractive in principle but presumes agreement on a networking model Fireactions does not use.

## Consequences

Existing Docker Profiles lose their warm pnpm store on the next Worker update; a cold install is the cost of removing a cross-job write path, and workflows that want a warm cache use `actions/cache` or a remote build cache over allowed egress. Operators of an existing Firecracker host must re-run the provisioner, because the CNI and containerd paths moved into EraInfra's own namespace and the nftables table did not previously exist; the old configuration is inert once it is no longer referenced. `Preflight` now fails hosts it used to pass — specifically, any host with no network policy — which is the point. Guests boot with `ipv6.disable=1` and readiness enforces it, because the nftables policy is IPv4 and a dual-stack guest could route around it.

## Considered and rejected

- **Keeping the CNI `bridge` plugin and filtering east-west with the `firewall` plugin:** rejected. The firewall plugin admits return traffic; it is not an egress filter, and same-segment traffic on a bridge never reaches the forward hook where a policy could see it.
- **A drop-policy base chain:** rejected. On a Worker that also runs Docker, a forward chain with `policy drop` breaks every unrelated flow on the machine. Scoped `drop` verdicts are final wherever they match and cost the rest of the host nothing.
- **Comparing the installed nftables ruleset as text:** rejected. The kernel normalizes rules — it merged two multicast ranges into one during live validation — so a textual comparison fails on correct hosts. Rule identity by comment is stable and still detects removal, reordering and insertion.
- **An EraInfra cache service with per-repository scopes:** rejected for now, on the architectural ground above and because it would be a new authenticated, multi-tenant storage surface to secure. Revisit only if the controller starts creating Attempts per `JobAvailable` message, which is where the repository first becomes known. **Superseded in part by [ADR 0007](0007-serve-the-actions-cache-protocol-from-an-s3-compatible-store.md)**, which decides an object-store cache fetched _inside_ the job, after `JobStarted` has already named the repository. The boot-time argument above is untouched and still rules out a per-repository cache device; nothing in ADR 0007 changes the isolation contract, because nothing writable is added to the Worker.
- **Leaving `provision-docker.sh` as it was and documenting the risk:** rejected. The volume was mounted into every job on the Profile; documentation does not make a shared writable store safe, and the Profile is meant to be the transitional path, not the one with the extra footgun.
